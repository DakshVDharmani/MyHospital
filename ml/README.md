# Patient risk-priority model

Predicts a patient's clinical urgency from their triage vitals, presenting
complaint, and medical history, so the doctor dashboard can rank a patient
queue by who actually needs to be seen first — instead of a hand-maintained
list.

## Folder layout

```
ml/
  database/            # raw dataset + generated splits — see "What's safe to delete"
  weights/              # model.joblib + metrics.json — this is what deploys
  src/                   # training pipeline (needs database/, not needed to serve)
  service/                # FastAPI inference service (needs weights/ only)
  requirements-train.txt  # deps for src/ only
  Dockerfile, railway.toml # deploy service/ to Railway
```

## The dataset

**[Hospital Triage and Patient History Data](https://www.kaggle.com/datasets/maalona/hospital-triage-and-patient-history-data)**
(Kaggle, user `maalona`) — 560,486 real ED visits from Yale-New Haven-affiliated
hospitals, backing [Hong et al., PLOS ONE 2018](https://journals.plos.org/plosone/article?id=10.1371%2Fjournal.pone.0201016).
Each row is one visit: demographics, arrival mode, ~200 chief-complaint flags,
~275 past-medical-history flags, ~80 historical-utilization counts (prior ED
visits/admissions/labs), triage vitals, and the **ESI** (Emergency Severity
Index, 1–5) a real triage nurse assigned that visit.

**Why this dataset and not the first one tried.** An earlier attempt used a
different, smaller Kaggle set whose "triage" label turned out to be an
arbitrary rule, not real clinical judgment — patients with heart disease were
*never* labeled urgent by it, and a model trained on it ranked a healthy
25-year-old above a 70-year-old with heart disease and hypertension. ESI here
is the real thing: an actual nurse's severity call, which is what "risk to
prioritize by" should mean.

**What's excluded, and why:**
- Every lab result and repeat-vitals column (`*_last`, `*_min`, `*_max`,
  `*_median` — 389 columns) is dropped. Those are measured *during* the visit,
  after the nurse already assigned ESI — training on them would be leaking
  the future into a triage-time prediction.
- `disposition` (admit/discharge) is the visit's outcome, also excluded as
  leakage.
- `race`, `ethnicity`, `religion`, `lang`, `insurance_status`,
  `maritalstatus`, `employstatus` are excluded — administrative, not
  physiologically relevant to acute risk, and a triage-risk tool has no
  business conditioning on demographics like race in the first place.
- `dep_name` and arrival date/time are hospital-operations metadata, not the
  patient's health.

**What's kept** (`src/feature_schema.json`, generated by `discover_schema.py`):
age, gender, arrival mode, the 7 vitals actually taken at triage
(`triage_vital_hr/sbp/dbp/rr/o2/o2_device/temp`), and ~559 numeric flags/counts
covering chief complaint + medical history + prior utilization.

## The target: risk score (inverted ESI)

ESI arrives as `1` (most urgent — resuscitation) through `5` (least urgent).
The model is trained to predict `6 - esi`, so **higher output = higher risk =
more urgent**, consistent with how the rest of this app already thinks about
priority (`priority.ts`, notifications). A predicted score is also rounded and
mapped back to a human label (`"ESI 1"` … `"ESI 5"`) for display.

## Why XGBoost, and how this one was tuned

XGBoost is a gradient-boosted decision tree ensemble: it builds trees one at
a time, where each new tree is fit to the *errors* of the trees so far
(specifically, the gradient of the loss with respect to the current
predictions — hence "gradient boosting"), so the ensemble incrementally
corrects its own mistakes rather than each tree working in isolation like a
random forest does. That makes it a strong default for this kind of data:
mixed numeric vitals + hundreds of sparse 0/1 flags, real missingness, no
need for feature scaling, and it naturally captures interactions (e.g. "high
heart rate *and* chest pain" mattering more together than either alone)
without hand-engineering them.

Practical choices made in `train.py`:
- **`tree_method="hist"`** — XGBoost's histogram-based split-finding, needed
  at this scale (390K training rows × ~580 encoded features); the exact
  split-search method would be far slower here for barely different accuracy.
- **Missing-value indicators on the 7 vitals.** They're missing 30-50% of the
  time (not every vital gets taken on every patient) — rather than just
  imputing the median and hiding that, each vital gets a companion
  `missingindicator_*` column so the model can learn "this wasn't measured"
  as its own signal, which is often itself informative in real ED data.
- **Early stopping instead of a fixed tree count.** Each candidate trains up
  to 800 trees but stops as soon as validation MAE stops improving for 30
  rounds — lets the search spend more trees on runs that need them, fewer on
  ones that don't.
- **A small random hyperparameter search (12 candidates) against a single
  held-out validation split**, not k-fold cross-validation. With 390K rows,
  a single validation split is already a stable estimate, and skipping k-fold
  avoids a 3-5x multiplication in fitting time for a large-data model that
  doesn't need it. Searched: max depth, learning rate, subsample ratio,
  column subsample ratio, min child weight, and L2 regularization strength.
- **`reg:squarederror`** objective with **MAE** as the both the early-stopping
  and model-selection metric — the risk scale (1-5) has genuine magnitude
  (predicting 4 when the truth is 1 is a much bigger error than predicting 2),
  which is exactly what a regressor (vs. a 5-way classifier, which would treat
  all misclassifications as equally wrong) is for.

## Running the pipeline

```bash
cd ml
python -m venv .venv && .venv/Scripts/activate   # or source .venv/bin/activate on macOS/Linux
pip install -r requirements-train.txt

cd src
python discover_schema.py   # (re)generates feature_schema.json from the real .rdata columns
python prepare_data.py       # cleans + writes database/{train,valid,test}.csv
python train.py                # trains, prints per-candidate val MAE, saves weights/model.joblib
python evaluate.py               # scores test.csv, writes weights/metrics.json
```

## Running the service locally

```bash
cd ml
pip install -r service/requirements.txt
uvicorn service.main:app --reload
```

- `GET /health` → `{"status": "ok", "model_loaded": true}`
- `GET /schema` → the exact feature list a patient object needs (there are
  ~570 of them — this is meant to be introspected, not memorized)
- `POST /predict` → one patient → `{risk_score, priority_label}`
- `POST /prioritize` → a list of patients → same, **sorted by descending
  risk with a `rank`** — this is the endpoint the doctor dashboard's queue
  would call.

A patient object doesn't need every field: anything omitted is treated as
unknown and imputed the same way the training data's missing values were
(median for numeric/vitals, most-frequent for everything else) — so a caller
that only knows the 7 vitals plus a couple of relevant history flags still
gets a sensible score, since an absent flag defaulting to "no" is usually
the right assumption anyway.

## Deploying to Railway

`ml/Dockerfile` only copies in `service/` and `weights/model.joblib` — never
`database/` or `src/`. Point a new Railway service at this repo with **root
directory `ml/`**; `railway.toml` tells it to build the Dockerfile and health-
check `/health`. Railway injects `$PORT` at runtime, which the Dockerfile's
`CMD` already binds to.

Test the image locally before trusting the deploy:
```bash
cd ml
docker build -t risk-service .
docker run -p 8000:8000 risk-service
curl localhost:8000/health
```

## What's safe to delete once you trust weights/model.joblib

- `database/` (the raw `.rdata` + generated splits) — training data, not
  needed to serve. It's already gitignored (the raw file is ~99MB, right
  under GitHub's 100MB hard limit — too risky to track anyway).
- `src/` and `requirements-train.txt` — the training pipeline; `service/`
  never imports from either.

Keep `weights/model.joblib` and everything under `service/` — that's the
whole deployable unit. To retrain later (new data, a schema change), you'll
need `database/` and `src/` back, which is exactly why this is worth keeping
as a separate git history / backup rather than deleting outright.
